BPSC AI Platform

Document 08 — Deployment, DevOps, Infrastructure & Production Operations

Version 1.0 | Implementation Specification

Purpose: Define how the BPSC AI platform is packaged, deployed, scaled, monitored, secured, backed up, and operated from MVP through production.

1. Executive Summary

Start with a production-capable modular monolith, not a large collection of independently deployed microservices. Separate API, asynchronous workers, scheduler/notifications, AI Gateway, database, cache/queue, object storage, and observability.

The backend must remain channel-independent so Telegram is only the first client; Web and Android can reuse the same application services later.

2. Production Architecture

TELEGRAM / WEB / ANDROID → API → APPLICATION SERVICES → POSTGRESQL

↘ REDIS / BULLMQ → WORKERS → AI GATEWAY → AI PROVIDERS

↘ OBJECT STORAGE

↘ NOTIFICATION WORKER → TELEGRAM

↘ LOGGING / METRICS / TRACING

Expensive OCR, evaluation, RAG-heavy generation and mentor tasks should normally be asynchronous.

7. Containerization

Use pinned runtime/dependency versions.

Use multi-stage Docker builds.

Run as non-root where practical.

Keep configuration outside images.

Add health checks.

Support graceful shutdown.

Use separate API and worker entrypoints.

8. API Deployment

Keep API stateless.

Store state in PostgreSQL/Redis.

Never rely on container-local uploaded files.

Use request/correlation IDs.

Use connection pooling.

Apply request-size limits and rate limits.

Return quickly for asynchronous operations and expose job status.

10. Job Reliability

Design for at-least-once execution.

Every job must be idempotent.

Use unique business operation keys where appropriate.

Use bounded retries and exponential backoff.

Set explicit timeouts.

Record job and correlation IDs.

Use priority where student-facing jobs require it.

Prevent duplicate expensive AI work.

11. Telegram Webhook Operations

HTTPS only.

Return quickly after accepting a meaningful update.

Persist/enqueue work before expensive AI processing.

Protect against duplicate updates.

Handle blocked users and deleted chats gracefully.

Keep Telegram SDK logic inside an adapter layer.

The domain layer must not depend directly on Telegram SDK types.

12. Database Operations

PostgreSQL is the transactional source of truth.

Use version-controlled migrations.

Do not manually change production schema as normal practice.

Monitor connections, locks, slow queries, storage and CPU.

Tune pgvector indexes from measured workload.

Back up regularly and test restoration.

13. Migration Policy

Create migration locally.

Run tests.

Apply to development.

Apply to staging.

Verify backward compatibility.

Back up production before risky changes.

Apply production migration.

Deploy compatible code.

Run smoke tests.

Prefer expand → migrate → contract: add compatible structures first, migrate data, then remove obsolete structures later.

14. Object Storage

Store handwritten images and source documents in private object storage, not PostgreSQL blobs.

Store object keys in the database.

Use short-lived signed URLs.

Validate file type and size.

Scan uploads when appropriate.

Keep originals for OCR/evaluation reruns.

Apply lifecycle/retention policies.

25. AI Provider Resilience

Provider adapters implement a common interface.

Set explicit timeouts.

Use bounded retries with jitter.

Do not retry non-retryable errors.

Support configured model fallback.

Track provider-specific failures.

Record model/provider on every evaluation.

A model change must never silently change scoring semantics.

26. Cost Protection

Set daily/monthly AI budgets.

Track cost by workflow and student where appropriate.

Use model routing.

Cache stable outputs.

Deduplicate jobs.

Limit upload count/size.

Limit retries.

Prevent worker loops.

Alert on abnormal token usage.

27. Security Baseline

TLS/HTTPS.

Input validation.

Rate limiting.

Parameterized queries/ORM protections.

Dependency/container scanning.

Admin audit logs.

Encryption at rest where supported.

Secret rotation.

Restricted production access.

28. Student Data Protection

The platform handles handwritten work and learning history. Treat these as sensitive operational data.

Collect only required information.

Define retention periods.

Support deletion workflows where required.

Restrict access by role.

Keep raw images appropriately protected.

Never expose one student's work to another.

Never use production student data in development.

Document what data each AI provider receives.

33. Infrastructure as Code

Define network/firewall rules, databases, Redis, storage, services, secrets references, monitoring and alerts as code as complexity grows.

Keep infrastructure configuration version-controlled and reviewed.

Avoid undocumented manual production changes.

34. Operational Runbooks

Create runbooks for API outage, worker backlog, AI outage, OCR degradation, evaluation-quality degradation, database/Redis/storage outage, Telegram webhook failure, cost spike, security incident, failed deployment and failed migration.

Each runbook should contain detection → containment → diagnosis → recovery → validation → post-incident actions.

38. Final Infrastructure Principle

Do not build infrastructure for the company you might become. Build a reliable platform for the students you have today, with clean boundaries that make tomorrow's scale possible.

INITIAL: MODULAR MONOLITH + POSTGRESQL/PGVECTOR + REDIS/BULLMQ + OBJECT STORAGE + AI GATEWAY + DOCKER + CI/CD

SCALE PATH: MORE WORKERS → QUEUE SPECIALIZATION → DATABASE/CACHE OPTIMIZATION → READ REPLICAS → DEDICATED SERVICES ONLY WHERE MEASURED NEED EXISTS
