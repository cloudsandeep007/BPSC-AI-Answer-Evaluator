BPSC AI Platform

Document 09 — Analytics, Metrics & Product Intelligence Specification

Version 1.0 | Implementation Specification

Purpose: Define what the platform should measure, how events and metrics should be structured, how AI quality and unit economics should be tracked, and how analytics should drive product decisions.

1. Executive Summary

Analytics should answer one central question: Are students actually improving because of the BPSC AI learning loop?

The platform must measure more than Telegram messages, users and AI calls. It needs telemetry connecting question → attempt → OCR → evaluation → feedback → skill change → next practice.

Use four layers: Product Analytics, Learning Analytics, AI Quality Analytics, and Business/Operational Analytics.

2. Analytics Principles

Track outcomes, not vanity metrics.

Represent important actions with stable versioned events.

Keep operational metrics separate from learning outcomes.

Make every AI result traceable to question, blueprint, prompt/model and evidence.

Protect student privacy and minimize personally identifying analytics.

Prefer cohort and longitudinal analysis over isolated daily numbers.

3. Analytics Architecture

TELEGRAM / WEB / ANDROID → APPLICATION EVENTS → ANALYTICS PIPELINE → REPORTING / DASHBOARDS

↘ PRODUCT

↘ LEARNING

↘ AI QUALITY

↘ BUSINESS / OPERATIONS

Operational PostgreSQL remains the transactional source of truth. Begin with PostgreSQL reporting tables and move to a warehouse only when scale requires it.

5. North-Star Metric

Recommended North-Star Metric: Weekly Active Learning Students (WALS).

Definition: a student who completes at least one meaningful answer attempt in a seven-day period that reaches evaluation and feedback.

Supporting outcome: percentage of returning learning students whose normalized/difficulty-adjusted performance improves over a rolling window.

12. Student Skill Profile

Maintain topic/criterion skill records containing skill_id, topic_id, criterion, proficiency, confidence, sample_count, last_practiced_at, last_improved_at and weakness_status.

Do not declare mastery from one excellent answer. Require sufficient observations and confidence.

13. Difficulty-Adjusted Learning

A 70% score on an easy question is not necessarily equivalent to 70% on a difficult question.

Store target and observed question difficulty.

Use difficulty as a covariate in progress reporting.

Compare students primarily with their own trajectory.

Track performance on novel questions to test genuine transfer.

Core measure: AI + OCR + storage + queue/compute allocation attributable to meaningful learning activity.

Track cost per completed evaluated attempt and cost per retained learning student separately from fixed operating expenses.

23. Experimentation

Define hypothesis first.

Define primary and guardrail metrics.

Assign users consistently.

Log experiment exposure.

Avoid changing several major variables without attribution.

Check duration/sample size.

Measure learning outcomes, not only clicks.

Document the decision.

Example: a weakness-based next question increases second-attempt completion without reducing answer quality.

28. Data Quality Rules

Registered/versioned event names.

Required fields validated.

IDs reference valid entities where applicable.

Detect duplicate events.

Version schema changes.

Make aggregate jobs idempotent.

Reconcile important aggregates with transactional counts.

29. Privacy

Use internal IDs instead of unnecessary personal identifiers.

Do not put handwritten answer text in ordinary analytics events.

Do not put raw prompts/responses in analytics tables unless required.

Restrict analytics access.

Apply retention policies.

Avoid exposing tiny cohorts.

Document third-party analytics data sharing.

34. Metrics That Should Not Be Primary KPIs

Total Telegram messages.

Total questions generated.

Total AI tokens consumed.

Raw app opens.

Number of feedback messages.

Session length without learning context.

Follower/member count alone.

These are diagnostic signals, not proof of educational value.

35. Event Flow

USER ACTION → APPLICATION SERVICE → VALID TRANSACTION → DOMAIN EVENT → ANALYTICS EVENT → AGGREGATION → DASHBOARD

Emit important events from application/domain services rather than reconstructing behavior from UI logs.

36. Claude Code Implementation Guidance

Create a typed event registry.

Create one shared event envelope.

Emit domain events from application services.

Persist events idempotently.

Build daily/hourly aggregation jobs.

Create reporting-service queries.

Create dashboard-ready APIs.

Add event schema tests.

Add reconciliation tests.

Keep analytics providers replaceable.

38. Implementation Sequence

Define event taxonomy.

Implement event envelope and validation.

Instrument the core learning loop.

Persist immutable events.

Build aggregates.

Build Product and Learning dashboards.

Add AI quality/cost dashboards.

Add subscription metrics.

Add experimentation.

Move to warehouse/BI only when justified by scale.

39. Definition of Done

Core learning actions emit versioned events.

Events are idempotent and queryable.

End-to-end student funnel is measurable.

Longitudinal learning improvement is measurable.

Topic/criterion performance is measurable.

AI quality is benchmarked against humans.

AI cost is attributable by workflow.

Subscription/revenue events are measurable.

Dashboards separate learning/product/AI/operations.

Privacy controls protect student content.

Aggregates can be rebuilt.

Metric definitions are documented.

Prompt/model releases can be compared with historical baselines.

40. Final Product Intelligence Principle

The platform should know not only how many students used it, but whether they complete the learning loop, where they struggle, whether the AI is reliable, what each interaction costs, and whether the product produces measurable improvement.

NORTH-STAR: MEANINGFUL LEARNING ACTIVITY + MEASURABLE IMPROVEMENT + TRUSTWORTHY AI + SUSTAINABLE UNIT ECONOMICS

If a metric cannot support a product, academic-quality, operational, or business decision, it should not automatically become a KPI.
